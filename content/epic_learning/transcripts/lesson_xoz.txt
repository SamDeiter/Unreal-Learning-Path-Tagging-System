Let's open up our arrow blueprint again and let's give our arrow some logic to move forward. If we think about our expected action, we can think of it as a causal relationship. For example, if we press 1, we want our arrow to move forward. So our cause is our key press and our reaction is the logic to make the arrow move. When UE4, the cause is called an event and Blueprints have what is called an event graph. This is where all our causal activity will occur. Let's go ahead and click into it by clicking on the Event Graph tab in our arrow blueprint. By default, Blueprints have BeginPlay, ActorBeginOverlap and TickEvents, as they are very commonly used. However, let's ignore them for now and find a clean place in our event graph. If we right-click, we can then type in Keyboard event and get a list of all the events relative to the keyboard. If we grab the one event, we can see it will give us a node that tells us if key 1 is pressed or released. What this means is that when one is pressed on the keyboard, an event or pulse will come from the pressed node. With this event, we can do all sorts of things. By clicking and dragging out from the pressed event, we can see a large list of the commands that can be initiated by this event. Let's go ahead and type Add Actor Local Offset and select the function. As you can see, we now have a node that will offset an actor's location in the world. If you look more closely at the node, you may notice the first input is set to Self. It will do this by default, and in this case it is what we want. However, you could also feed it with a different actor. Later, this will be more important, but for now, realize that Self is like saying when one is pressed, move me. Now, let's look at the second input, New Location. Here we can see the effective action of our node. It will offset our location in the scene. For now, let's enter one in the Y input. To recap, we are now listening for the one key to be pressed. When it is, we want to offset our blueprint location by one unit on the Y axis. Unfortunately, we are not quite done yet. By default, in the standard template, key input is disabled. Because of this, we need to enable it. We'll click in the event begin play in the event graph list to zoom to it. Now, simply drag out from the begin play node and select the enable input node. Leave the target as Self. Then for the player controller, use the get player controller node to feed it. At this point, you wrote your first reactive blueprint. Let's go ahead and test it out. Save compile and close the blueprint window and press play. Notice that you now have all your arrows moving, right? Wrong. Only one is moving, but why? The entire point of a blueprint is that they should all act exactly the same, right? Well, yes, this is true. But we need to investigate our blueprint again quickly to see what's happening. Let's reopen the arrow blueprint. Now, click on the one event in the graph list. As we can see, there are some options in this input event we need to look at more closely. The first check box is set to consume. What this means is that the first actor to use this event blocks all subsequent actors from using it. Ideally we would leave this with consume being true or checked, but for this example, we will need to uncheck it and set it to be false. Now if we compile, save and hit play, we should see that all of our arrows move forward by one unit each time the one key is pressed. Feel free to add in more arrow instances and retest. No matter which way they face, you should now see all of your arrows running in their own independent courses each time you click one. Congratulations! This is a huge first step, and you should start to see the possibilities even from this simple example. Everything from here forward will be building upon this simple concept.
