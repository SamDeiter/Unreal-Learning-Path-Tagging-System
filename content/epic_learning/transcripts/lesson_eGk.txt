Before we jump into creating and working with our data inside of Unreal, we should take a moment to get an understanding of the different types available and then look at why they can be so useful. There are two types of external files that you'll often see used when working with Unreal or even other game engines making them a versatile tool to understand. The first is going to be the CSFee file, short for comma separated values. As the name suggests, the data here is separated by commas making it very intuitive to format your data if you're using simple data types. They tend to look something like this and are mostly easily created or edited using a spreadsheet editor, just like Excel or Google Sheets. Although if you don't have access to these, you could still use something like Notepad as seen here. The second type is the JSON file. This one is short for JavaScript object notation. This file type can be created or edited using any plain text editor, again, just like Notepad, and the data inside of them tends to look something like this. And some useful things to know about when working with this data file is that there are a bunch of free online JSON validator and formatocytes. I won't make any personal recommendations here, but a quick Google search will return a large list of choose from, and they're all great to ensure that you catch simple to overlook syntax errors before importing your file to your game engine. So a lot of the differences here between the different file types that you can use will come down to as with most things personal preference. The more general differences though tend to be that the CSFee files are much more lightweight, compact, and provide better readability for simple data. This tends to mean that they work really well for files that can become extremely large, like translation sheets where the complexity is usually very simple, but can contain a lot of information. In comparison, JSON files offer better versatility, scalability, and are much easier to read when working with complex data, especially data that has nested information or is kind of hierarchical in nature. This is usually great for data such as branching dialogue or quest systems. As well as their general use cases, it's also going to be worth considering the people on your team and how easy it will be for them to work with and understand the data types you're developing. As an example here, you'll often be working with writers, translators, designers, all of whom may not be familiar with the structure and syntax of something like JSON. It's very easy for people to miss a single comma or place the wrong type of bracket in the JSON syntax. Again, this is where those parser or validators come in very handy, whereas in comparison, using something like a CSV file inside of Excel, the end user simply needs to type their information into the correct cell. There's a lot less to get wrong. So these are the external data types that we'll be working with, we'll be seeing mostly CSV just due to the types of data we'll be working with in the project. And then finally, we have our float curves, unlike the other data types, float curves are completely independent and don't need any external files. They allow you to easily create custom float curves using the Unreal Curve Editor, and data can then be extrapolated from the data curve at certain points along that curve and return the related float value at that point. So all of these different data types can be incredibly useful to make workflows easier to manage, update, and even somewhat automate. If you imagine trying to write an entire dialog system in the editor simply through the use arrays or structs or maps, depending on the data required, then imagine that something happened to the project to corrupt one of those dialog holders requiring a potentially hours of work to be redone or attempting to grab things from a recent repo push. The same could apply to your stat and quest systems, language translations, or even setting configurations. All of these can easily be stored inside of either a CSV or JSON file, brought into the engine as a data table, and then have all of the required details pulled when needed through a simple lookup call. You also get the added benefit of allowing people who don't necessarily need to be working inside of the engine, like those aforementioned writers, translators, and so on to simply work in something like notepad or Excel, cutting down the number of users dependent on syncing their work with other developers. Then we have assets like the float curve, which is perfect for adding flexibility to otherwise repetitive tasks. These are great for adding animations to things like UI elements where otherwise you'd need to recreate similar animation logic for various elements. With a float curve you can simply define the animation logic in the code, just the once, and then simply pass in the desired float curve that you've created for your different UI elements. They're also used for things in game, such as lurping rotation or movement speeds of dynamic cameras, character movement, jump accelerations, and much more. One caveat to mention here though, as with anything, when programming data assets in the general term are not the absolute solution to everything they will over complicate things at times, things like the data tables do have their drawbacks, such as being slower than data assets, or being unable to utilize a parent child hierarchy. Similarly, data assets can prove difficult to manage larger entries and generally to navigate the interface as they're basically intended to represent a single row that you'd find in a data table. So this is to say that as with anything you'll need to come to recognize where and when integrating something like a data workflow to your project will be beneficial on a per project and per task basis.
