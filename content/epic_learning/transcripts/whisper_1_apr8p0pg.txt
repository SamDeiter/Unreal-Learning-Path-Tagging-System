Macros are the primary way to integrate C++ code with Unreal Engine and expose functionality to the Editor. They provide metadata and functionality for Blueprints, networking, reflection, serialization, and other systems. U-class, U-struct, and U-NM are used to expose types to Unreal Engine, both for using in Blueprints and in the Editor. U-property exposes class members to Unreal Engine, both for Blueprints and in the Details panel. You can determine where the property can be viewed, accessed, and edited. It enables automatic memory management of U-object pointers. It also enables networking and serialization functionality. It's very important that all class properties that reference U-objects be either a U-property reference or a weak pointer type so you don't get crashes if you try to access them after they get garbage collected. And lastly, U-function exposes functions to Unreal Engine. These are the foundational building blocks of Unreal Engine. Unreal has its own standard library. You don't use the standard library from C++ at all. This allows better editor integration, serialization support, and portability between platforms. For numbers, we have floats and doubles, same as regular C++. For integers, however, we have explicitly sized ints and U-ents. The sizes of the plane int can vary between platforms, so it's important that for serialized and replicated properties, you always use the explicitly sized integers. You can use plane ints if the variable isn't serialized at all, for example in four loops, but it could happen to always prefer the explicitly sized ones. And numerables can be created and exposed to the engine. Structs are like classes, except they are only expected to keep plane data and can't have any blueprint functions on them. Unreal has several string types depending on your needs. F-string is your standard plane string. It's a wrapper for a white character array, and it is mutable. F-name hashes and caches strings in a global map, which is then referenced from F-name variables. Because they just store the intex of the string, they allow superfast comparisons. They also have an index at the end, which you can increment without creating new strings. They're case insensitive, and are best used for names and paths. F-text are strings with built-in localization support. They get collected by the Entience Localization System for you to easily translate from a simple source. These should be used for any user-facing text. Unreal has the standard collection types you would expect from any programming language, like arrays, maps, and sets. Their template can be exposed to blueprints and even support different memory allocators like Threadsave, Heap, or Inline allocation. It also comes with ease of use transform types that support blueprint and replication. There are lots of utility functions for these types in the F-Math library. U-object is the lowest level Unreal object which gets memory managed by the engine. All classes extending in should be prefixed with a U. An actor is anything that can be placed in a level. Extending classes should be prefixed with an A. Actors get automatically loaded and destroyed with their parent level. You can dynamically allocate new actors with the spawn actor function and destroy them with the destroy function. Besides making a new type of actor, you can also add functionality to them with components. Components contain the actual representation of what is placed in the level. The parent actor is mostly a container. A component can be either a U-acture component with no enrolled representation or U-scene component which has a transform relative to the parent actor. Actors can have multiple components of either type and one root scene component from which all transforms are based from. Components are great for adding sets of functionality to different actors without modifying their inheritance hierarchy. You should only allocate new U-objects with a new object function and actors with a spawn actor function. U-objects get automatically destroyed when no other objects are referencing them. Actors can be removed from a level with a destroy function but the garbage collector will be what eventually releases the memory. Never try to manage the lifetime yourself through keywords like new, delete or smart pointers which manage lifetime. A very common mistake to make with U-objects is to have strong pointers to them without the U-property micro. They're not visible to the girl's collector so the object can collect it and your pointer left pointing to invalid data and memory which can be very hard to debug. We have two sorts of smart pointers in Unreal Engine. U-object facing once on the left and none U-object facing once on the right. It is important that you never use the pointers on the right on any U-objects. Interfaces allow optional functions to be implemented by unrelated classes. This is unlike other programming languages where classes must implement every function in an interface. In Unreal, an interface function can be called on any object and it will only be called if it's implemented. Interfaces can be declared in either C++ or as a Blueprint. It is, however, recommended to create interfaces in C++ so both C++ and Blueprints can use them as Blueprint interfaces can only be used by other Blueprints. Static function libraries allow you to create static functions that can be called from anywhere. These are a good option for adding functionality to structs. Data objects give you a way of organizing and loading in data. They're a great way to structure your gameplay data. Data assets are generic containers, similar to data only Blueprints. Data tables have easy import and export functionality and support Unreal types. You can also create curves as assets and reuse them in multiple places. Delegates and events allow other objects to subscribe to a relevant event. These can be created from either C++ or Blueprint. However, if you want to subscribe to them in C++, then they need to be implemented in C++. Subsystems allow you to extend functionality easily and in a modular way as they follow the lifetime of Entic classes. They're like components to some Entic classes which you can access from anywhere. It keeps your code modular, easier to maintain and easier to share between projects. Lastly, we have the asynchronous task graph, which is an Engine Managed task graph which you can use to run work on multiple CPU cores or for asynchronous threaded work. It uses a thread pull internally and multiple Engine systems already make use of it. In Unreal Engine, loading assets is mostly handled for you. Things either load in with a map or you can request an object be loaded from a software reference. Objects then get unloaded by the garbage collector when nothing references them anymore. Anything that is referenced normally, as in through a heart reference, is automatically loaded recursively with the parent asset. This is convenient but can backfire if you're not conscious of your references. A common pitfall is to reference too many things, where some assets can end up accidentally pulling in half of the project's other assets, which increase slow times and memory, both for the editor and for shipping builds. Be mindful of your references and use soft references and interfaces to reduce hard dependencies. The garbage collector automatically destroys objects that are either unreferenced or pending kill. It runs about once a minute, but you can override that. The garbage collector uses the Mark and Sweep method. The marking and sweeping is heavily multithreaded and happens in a single frame, while the actual object destruction is time-slived and happens over multiple frames. Unreal comes with a robust foundation, usable for most game types, which we call the gameplay framework. It supports multiplayer or the box, natively and robustly. We recommend you take advantage of the gameplay framework, instead of designing your systems around it, to really get the most out of Unreal. The game mode is a per-level object that defines the rules for that level, like what pawns to spawn, with HUD class and so forth. One of the first things you do on a new project is to create your own game mode class to override. For multiplayer games, this object instance only exists in the server. It defines the rules for the session, who can join, spectator rules, etc. It will not survive a hard level transition, so it's not good for storing persistent data. For that, you can use the game instance. Every client has a game instance that persists throughout the entire application's lifetime. It's a global single-ton that you can access from anywhere. You can either extend it for your project, or alternatively, you can create a game instance sub-system, which is kind of like a component for the game instance class. The game state is an object that is replicated from the server to all clients. If game mode is the object which states the max team points needed to win a match, then game state is the object you'd use to keep track of the current points. It also keeps a list of all the player states. The player state is the game information that is specific to a given player. It's replicated from the server to all clients and stores things like player name, score, and pink. But of course, you can extend this class and add your own data to it. A pawn is an actor that a player can control. It's generic and doesn't include much more than replication in it. A character is a type of pawn which has a movement component, a skeletal mass, and it can walk, run, fly, and swim. A pawn is processed by a controller, which handles the inputs and commands to send to the pawn to control it. The controller can either be a human player or AI. You can switch possession of pawns at any time during gameplay, like for a player to switch from controlling the character to controlling the Wii and call the characters in. The controller is the brain of a pawn. Each player controller is associated with a specific player in their player state. And the player controller only exists on the only client and the server. The player controller allows the client to communicate with the server. To allow the most flexibility, you should always handle all input in the controller class and not in the pawn, that allows you to more easily switch out the player controller with an AI controller without having to handle it in the pawn itself. It handles its input through the input component. The input component binds input commands to game functionality. It is gradually being replaced by enhanced input. The movement component translates user input to in-game movements. It accounts for replication and it attempts to predict movement and account for lag. The movement component can be of different types, projectile, interpolated, pawn, character, or vehicle. It can also be extended to a provide custom movement. The cheat manager centralizes development, cheat and debug commands in a single class. It gets compiled out and released built, so it's a safe way to add debugging functionality to your project safely without risk of shipping with unintended functionality. You can set which cheat class to use in the player controller. We have a robust ticking system in Unreal Engine. Each actor and their components can register to tick. You can even add ticking to you objects. Ticks can run during different tick groups, like before physics or during physics. It's smart to take in during physics if you're not using transforms or collisions. You can define tick rate, tick dependencies, and enable or disable ticking on a per object basis. Ticks run single-thread it so they can be a common point of congestion for games. Consider reducing tick frequency for objects that don't need to tick a reframe. The gameplay ability system is a multiplayer ready framework for handling gameplay abilities in a modular and robust fashion. Mass allows you to define and manage a large number of game entities through distributed execution and state graph. And lastly, game features plugins allow you to safely enable and disable functionality at runtime. These plugins depend on your project, not the other way around, so they allow your project to be feature agnostic, where the game features plugins, register themselves into your game. By default, you can extend gameplay functionality by simply adding components to existing actor classes, but you can also call functions or interfaces for deeper integration. Unreal Engine comes with built-in networking support out of the box. It's based on client and server type networking, where the server can either be another game instance or a dedicated server which you can run as a headless application. The networking framework does all the heavy lifting for you, like handling sessions, connections, and communication on each platform. Actors can easily be replicated to all clients with a simple checkbox, and you can mark each property you also want to be replicated. RAP notify allows you to execute some logic in response to the value of a replicated variable changing. For networking, we have the concept of ownership, so only actors that are owned by the player controller are the ones that can send data to the server, while the server can send data to everyone. You have the option of using the replication graph plugin. The replication graph allows you to set rules for what makes an actor relevant to other multiplayer clients, like based on distance, visibility, or other things. We use this on Fortnite to enable multiplayer matches between up to 100 players efficiently. Then we have remote procedure calls, or RPCs, which allow you to call functions on different clients. You can mark an RPC to be run reliably, which will make sure it gets to its target destination, or you can keep it as unreliable, in which case the call could get dropped during heavy traffic.
