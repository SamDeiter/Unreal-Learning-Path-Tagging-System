Olá, e boas-vindas a Being Play, um curso de integração da UE5 para desenvolvedores. Sou Arran Langmead, desenvolvedor de conteúdo sênior na Epic Games. Hoje, falaremos da criação de efeitos visuais na UE5. Os efeitos visuais na Unreal são criados com a ferramenta Niagara, mas há outros componentes menores que contribuem para esses efeitos. Este vídeo aborda os componentes desse sistema e os outros recursos que o tornam mais que só uma ferramenta de efeitos de partículas. Embora muitos elementos formem o efeito de partículas, o ativo inserido no mundo é chamado de "System", ou sistema. Os outros ativos criados são componentes individuais dele. Assim, podemos reutilizá-los com facilidade em vários sistemas e trabalhar neles fora do controle de versão. Embora isso resulte em ferramentas mais complexas, elas são mais versáteis e escaláveis. Se o sistema é o contêiner de um efeito de partículas, que pode ser inserido no mundo, dimensionado e depurado, os menores componentes são os "Emitters", ou emissores. Cada emissor tem um ciclo de vida e etapas que pode percorrer, mas fica dentro de um sistema único. Podemos reutilizar emissores em vários sistemas, o que facilita a reutilização de tudo o que você cria. Eles geram "Particles", ou partículas, que contêm coleções de variáveis, e tendem a ter um renderizador atribuído, como sprite, fita ou malha estática. A lógica para sistema, emissor e partículas é controlada usando "Modules", ou módulos, que são pequenos pacotes de lógica que controlam como a partícula se move pelo espaço, a duração e com o que ela interage. É possível dimensionar os sistemas de partículas usando as ferramentas de escalabilidade e depurá-los de várias formas para otimizar e descobrir quanto as coisas custam. Agora que temos a visão geral do Niagara, vejamos os elementos individuais. A maioria dos efeitos de partículas tem três etapas: sistema, emissor e partícula. Cada etapa tem um período de surgimento e de atualização. Para o sistema, temos "System Spawn" e "System Update". Para emissor, temos "Emitter Spawn" e "Emitter Update". E para partículas, temos "Particle Spawn" e "Particle Update". A etapa de atualização para sistema, emissor e partícula ocorre em todos os quadros. A etapa de surgimento ocorre na inicialização de cada um dos elementos. Quando temos um sistema inserido no mundo, o "System Spawn" é ativado uma vez no início do ciclo de vida do sistema. O emissor é gerado uma vez para cada emissor dentro de um sistema. Se houver um sistema com três emissores, terá um "System Spawn" e três "Emitter Spawns". Sempre que um emissor criar uma partícula, teremos um "Particle Spawn" por partícula e "Particle Update" atualizará a partícula a cada quadro. A frequência de chamada dos eventos aumenta muito conforme avançamos na cadeia com o sistema disparando uma vez a cada quadro, o emissor disparando uma vez para cada emissor a cada quadro e a partícula disparando cada partícula de cada emissor a cada quadro. Podemos criar emissores como ativos independentes que só existem num sistema. Por exemplo, posso criar um sistema "Empty"… E posso mandar que comece a gerar partículas. Porém, esse emissor só existe neste sistema no momento. Se eu quiser, posso promover o ativo a um ativo independente que ficará no Content Browser. Feito isso, poderei reutilizar esse emissor em vários sistemas. É possível modificar os emissores em cada sistema com variáveis expostas e mandar que variáveis específicas herdem dos dados do sistema. Por exemplo, em "Emitter State", herdaremos das configurações do console em vez da zona do emissor. Podemos alterar essas configurações clicando no menu suspenso e alterando para "Self" para podermos especificar o ciclo de vida deste material específico em vez de copiar o sistema inteiro. Também é possível compartilhar os dados com esta hierarquia. Todo emissor do sistema pode acessar os dados armazenados no nível do sistema. Ou seja, se houver mais de um emissor, como aqui, posso criar um parâmetro de sistema que será compartilhado com todos os emissores. Além das seções Spawn e Update, há a guia de "Properties", ou propriedades, para o sistema e o emissor. Ela permite definir atributos genéricos em sistemas e emissores individuais, como se o sistema ou emissor está no espaço local, determinístico, e o alvo de simulação que queremos usar. O sistema também tem "User Parameters", variáveis que podem ser expostas ao Blueprint e ao editor no jogo. Se eu criar uma variável, digamos do tipo booleano, nomeá-la e compilar, quando clicar na variável dentro do editor… O parâmetro de usuário exposto será indicado aqui. Ao usar emissores predefinidos, você verá que há ícones de cadeado ao lado de vários dos módulos que está usando. Esse cadeado indica que o módulo foi herdado do emissor pai. Se eu clicar com o botão direito e acessar "Show in Content Browser", o ativo específico aparecerá no navegador. Podemos clicar duas vezes e modificar os parâmetros base deste emissor. Você também pode interagir com sistemas, emissores e partículas de várias formas. Há uma linha do tempo integrada no editor que permite deslizar para frente e para trás num efeito de partículas específico. Isso não é uma linha do tempo de verdade. Ela só calcula as partículas nesse estado e nesse momento específico. Ou seja, se "Determinism" não estiver selecionado, o que significa que as partículas aparecerão com os mesmos parâmetros dentro de um sistema aleatório, será diferente se você deslizar para trás. Como pode ver aqui, se eu deslizo para frente, há uma progressão padrão. Ao deslizar para trás, ele recalcula e produz um número aleatório diferente. Se definirmos "Determinism" para o projeto, poderemos deslizar para frente e para trás sem alterar o resultado. Na maioria das vezes, você gera partículas com a configuração "Emitter Update", usando "Spawn Rate" ou "Spawn Burst" ou um gerador personalizado. Você também pode usar emissores para gerar outros emissores. Neste exemplo, temos um "Location Event" base sendo gerado e duas partículas sendo geradas a partir dele. Podemos ativar e desativar emissores para ver onde são cada um está sendo gerado. As bolhas geradas aqui são jogadas para cima e depois descem e há uma fita extra que acompanha o rastro e alguns brilhos produzidos depois. O evento base tem um módulo "Generate Location Event", que permite enviar eventos de posição a outros emissores. Para usar isso, podemos adicionar um "Event Handler" que recebe a posição do evento e a aplica a esta partícula específica. Vários emissores podem acessar o mesmo evento, o que permite compartilhar a informação. E você não precisa só enviar eventos de posição. Também pode gerar outros eventos. Digite "generate" e pode usar "Collision Event" ou "Death Event" para gerar os diferentes tipos de evento. Podemos criar sistemas no Content Browser. Clicando com o botão direito, escolha "Niagara System". Também há os outros ativos que você pode criar no menu suspenso "FX". Há muitos ativos que você pode gerar como ativos independentes. Isso é bem útil, pois permite que faça o check-out desses ativos individuais e evita a contenção de check-out. Ou seja, várias pessoas podem trabalhar no mesmo projeto sem atrapalhar ninguém. Os módulos são os pilares que formam todo sistema de partículas que usa o Niagara. São pequenos pacotes de lógica criados usando um editor de nó. Você pode abrir o editor de módulo clicando em qualquer um destes módulos. Quase toda partícula que está dentro da Unreal é formada por módulos criados com este editor de gráfico. Eles parecem intimidantes, mas, quando começar a entendê-los, verá que não são tão assustadores assim. Bem à esquerda, temos uma entrada e, bem à direita, uma saída. Entre eles, temos a lógica formada por uma série de "Gets", que são os "Map Gets", que permite acessar dados, e "Map Sets", que permite definir dados. No caso de um código grande como esse, você terá muitas opções diferentes como parte deste único sistema. Por exemplo, aqui temos um "Static Switch" que define o tipo de "Velocity Mode" que queremos usar para este sistema. Embora pareça bem complicado, o nó "AddVelocity" não tem muitos dados dentro dele. Além disso, podemos ter vários "Gets" e vários "Sets", podendo dividir o sistema de partículas em muitos pacotes menores. O sistema "InitializeParticle" é grande, mas foi segmentado em pequenas seções como "Position", "Mesh Scale", "Sprite Attributes" etc. Podemos adicionar variáveis ao "Map Get" ou "Map Set" clicando no "+" e escolhendo um tipo de variável, como "float" ou "vector". As variáveis também têm namespaces, que definem o caso de uso e persistência. Ao clicar com o botão direito, você pode alterar o namespace para operar em um sistema diferente. Clique com o botão direito numa variável e vá até "Change Namespace" para alterar o namespace que deseja usar. Aqui, podemos especificar se o vetor está no nível do sistema, emissor ou partícula, se é uma variável local mantida só neste módulo ou se a variável é temporária, ou seja, ela tem a duração do quadro. Podemos adicionar um modificador ao namespace para ter mais informações. Expor variáveis assim permite criar partes padronizadas de lógica que você pode reutilizar em vários emissores e sistemas. Como pode ver num módulo como "Initialize Particle", o usuário pode definir muitas variáveis, dando a opção para muitas variações e controle sobre todas as variáveis. Por exemplo, tenho "Uniform Sprite Size" definido como uma variável explícita, mas também posso mandar que a variável seja derivada de outra variável. Digamos que eu queira expor como um parâmetro de usuário. Posso criar uma variável "float" no usuário e nomeá-la "Custom Size". Então, em "Inicialize Particle", vou até "Uniform Sprite Size" e defino como a variável "Custom Size". Isso conecta essas duas variáveis, de tal forma que a "Uniform Sprite Size", em "Initialize Particle", esteja vinculada ao parâmetro de usuário personalizado. Também posso realizar operações diferentes nessas variáveis. Por exemplo, posso usar um lerp entre dois parâmetros "float", com base em outro. Você também pode definir como uma expressão direta, que permite escrever a mesma fórmula, mas como um HLSL personalizado. Ao começar a criar os próprios módulos, é melhor você criá-los num sistema ou emissor existente. Depois, você pode deixá-lo mais usável em diversos sistemas e emissores. Para criar um sistema local, pode usar um "Scratch Pad", como visto aqui. Já tenho alguns criados. Quando estivermos satisfeitos com ele e quisermos usá-lo em mais de um sistema, podemos promovê-lo a um ativo independente. Para isso, vamos até "Local Modules", e este é chamado de "Scratch Module 2". Clique com o botão direito e em "Create Asset". Ele solicitará que você adicione o ativo ao Content Browser. Pode escolher um novo local e salvar. Agora poderá reutilizá-lo em vários emissores e sistemas, mas lembre-se que você criou um ativo independente. Ele está compartilhado com os sistemas e emissores em que o colocou. É aí que os outros sistemas que temos podem ajudar. Para começar, há várias opções de coleta de dados. Nos módulos, podemos obter muitos dados de amostra de fontes diferentes. Por exemplo, em "Camera", podemos obter a posição atual da câmera. Podemos obter o campo de visão e, em "View Properties GPU", há ainda mais informações sobre ele. Também podemos acessar "GBuffer", que significa que temos acesso a todas as etapas de buffer, como "Base Color", "Custom Depth", "Scene Color", entre outros, dentro do sistema de partículas. Também podemos ler malhas do esqueleto e malhas estáticas. Podemos ler dados de textura e até criar grids e obter as posições relativas de outras partículas. Para concluir, temos um nó "Custom HLSL", como o que se encontra no editor de material. Ele permite escrever HLSL personalizado pelo próprio módulo. É possível renderizar uma partícula de vários modos após gerá-la no mundo. O mais comum é usar o renderizador sprite, mas também há fita, malha, caches geométricos, luzes e até atores completos, que podem conter uma lógica de Blueprint própria. O que será renderizado é definido pela aba "Render". Neste emissor específico, estou usando um "Sprite Renderer" para gerar esses pontinhos. Você pode gerar mais de uma coisa por partícula. Podemos adicionar um sprite e outro sprite em cima, renderizar uma malha ou até adicionar a luz. Aqui eu escolhi "Light Renderer", aumentei o "Radius Scale" e aumentei a cor. Agora todas essas partículas estão emitindo luz. A maioria dos renderizadores exige um sistema para funcionar bem. Por exemplo, "Ribbon Renderer" pode exigir atualizações com parâmetros como "Update Beam" ou "Spawn Beam". Ao usar o módulo "Initialize Particle", você verá que muitos dos parâmetros são para tipos específicos de renderizadores. Por exemplo, "Mesh Attributes" para malhas e "Ribbon" para fitas. Cada tipo de fita tem "Bindings" que permitem especificar a variável usada para controlar um parâmetro específico. Neste exemplo, temos "Position Binding" definido como "PARTICLES Position", que é o mesmo para o "Light Renderer". Temos "Position Binding" aqui. Se queremos dois parâmetros diferentes para este efeito, podemos revincular "PARTICLES Position" de um dos tipos de renderizador para ser outra variável e definir de forma independente. Para os renderizadores de sprite, fita e malha, você tem acesso à configuração de material, que permite especificar o material usado na superfície específica. Ao abrir editor "Material", você verá muitos controles de material para partículas. Por exemplo, temos "Particle Color", que pode produzir R, G, B e Alfa, definido direto usando "Set", "Particle" e "Color". Também podemos obter "ParticleDirection", "ParticleMacroUV", "ParticlePositionWS" "ParticleRadius" e vários outros parâmetros de partícula. Além disso, temos acesso aos parâmetros dinâmicos que podemos definir no sistema de partículas para ser coletado pelo material. Lembre-se que, ao usar um material num sistema de partículas, você habilitará o uso de sinalizações para esses tipos de efeito. Temos os modelos antigos do Cascade e os novos tipos de renderização do Niagara indicados aqui. Quanto mais você usar, maior será o uso de sinalizações habilitadas e elas não serão desabilitadas quando removê-las. Toda vez que criar uma sinalização de uso, você gerará outra permutação de material, que aumentará os tempos de compilação de shader. Não quer dizer que seja ruim. É só algo para lembrar ao criar materiais para os efeitos de partícula. Por fim, os materiais não precisam ser definidos apenas aqui. Também podem ser definidos na aba "User Parameter". Basta criar um tipo de material, definir o padrão desejado e, no "Sprite Renderer", podemos definir essa interface de material específica como o material padrão. Temos várias opções de depuração que você pode usar para analisar o sistema e os emissores. A mais fácil de usar é o botão "Performance", que está na aba "Performance" no sistema Niagara. Ative-o para ver todos os custos associados a cada módulo. Este específico é um simulador fluido, então os custos são altos, em especial em "Solve Pressure", que especifica 3 ms. Essa aba também ajuda a encontrar módulos de alto custo dentro do sistema. Além da aba Performance, temos o Attribute Spreadsheet, que permite conferir todos os dados de todas as partículas dentro de um emissor numa exibição de gráfico. Para acessar, clique no emissor específico que quer depurar. No menu suspenso "Debug", clique em "Attribute Spreadsheet". Clicando em "Capture"… ele congelará o sistema de partículas e dará todos os dados dele no ponto atual. Como pode ver, temos a idade de todas as partículas e as cores. Também temos tamanho de sprite, tempo de vida… posição e muito mais. Ele mostra todas as variáveis que temos em cada partícula e é uma exibição bem detalhada do sistema de partículas atual. Pode-se depurar sistemas de partículas de modo visual usando as opções Debug Drawing. Alguns módulos já têm opções de depuração disponíveis. Passando o cursor sobre este olho em "Point Attraction Force", você pode habilitar ou desabilitar "Debug Drawing" no item. Quando habilitamos, surge uma esfera de depuração ao redor do objeto e há opções de depuração traçadas aqui no canto inferior direito do módulo. Para criar opções de depuração próprias, basta usar o valor local "DebugDraw". Daqui, pode definir os formatos necessários e estipular as posições como quiser. Para criar a ativação, basta adicionar um "Static Switch" com "Enum Constant" definido como "Function.DebugState". Por fim, temos o Outliner de depuração. Clique no sistema dentro da cena e no botão "Debug" para abrir o depurador geral. Ele permite executar, pausar, definir a velocidade do sistema de partícula e controlar diversos parâmetros, tudo dentro deste prático menu suspenso. Você também pode acessar "FX Outliner", mudar para "Performance" e executar um teste de desempenho e conferi-lo em "Session Browser" se necessário. A escalabilidade permite controlar o custo dos sistemas de partículas na plataforma que está usando e na configuração General Quality. Ela fica em qualquer sistema de partículas dentro do editor. Clicando em "Emitter Update", você verá que "Scalability Mode" está definido como "System", ou seja, a escalabilidade geral será derivada das configurações do console. Também podemos definir como "Self" para termos o controle manual. Ou recorremos às propriedades de "System", adicionando um tipo de efeito específico, que permite agrupar as configurações de escalabilidade do sistema de partículas. Você pode criar tipos de efeitos ou usar os que já estão gerados nas configurações do projeto. É possível ativar e desativar cada uma das configurações por plataforma e definir "CVar Conditions" para que as configurações mudem. Você pode definir distância projetada e distância de oclusão com facilidade, usando essa configuração. Depois de pronta, você pode usá-la nos devidos efeitos de partícula. A pré-visualização "Scalability" no topo permite visualizar as configurações de escalabilidade para este sistema específico e adaptá-las às necessidades. Você pode alterar o tipo de efeito entre várias opções para conferir como cada um modifica o sistema que temos aqui. Com isso, encerramos a visão geral da criação de efeitos visuais usando o Niagara na UE5.
