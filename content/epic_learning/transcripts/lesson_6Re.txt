With a project containing maps this large, it takes a clever solution to be able to collaborate on a level this size and stream the various zones as needed into an experience that can handle this amount of data. Creating open worlds that a user can explore takes a number of tools to come together to solve this. Let's jump back into our small city map and have a look at how this was done using world partition and data layers. On the right side is the world partition window showing us our map as well as where we are located within it. World partition is a grid based streaming system that allows multiple instances of the same level to be modified in context. Each of these squares has an identifiable cell number and we can view that by turning on the cell coordinates. If you wanted to make sure you had all your computer's performance dedicated to one or several cells, we can unload them all, then load only the ones that we are wanting to work in. It is these cells that the system will load and unload as the user navigates around the scene and it does so automatically. The organization of these assets is found in the data layers window. To open, go to Window, World partition and select Data Layers Outline. Here are the various layers that are being used to build this map. See that when I select one of the layers, it is initially loaded and is initially visible is set to true. Here too is the collection of assets that are loaded and unloaded as they are needed. If we were to navigate to the big city map, we'd have to explicitly select the cells we want to work in and load them manually as the amount of needed resources is much larger. But in small city, everything is set already to visible. To add actors to a specific layer, we could just drag and drop them from the world outliner directly into one of our layers, giving us further control of how they are managed. Along with World partition and data layers, the city sample project takes advantage of the OFPA or one file per actor system. This has greatly assisted with team projects utilizing source control as Unreal Engine will write a separate file for every instance of an actor that is placed in a level instead of writing it all to one large map file. The great part about the implementation of this workflow is that nothing has changed for the building of a map. Every artist and developer utilizing source control can be on their own system working inside of the same map and their modifications are being written to the actors file, preventing any encountering of conflicts with committed changes. Editing these files is as easy as right clicking on them, choosing edit, and select the asset that you want to edit. Then when you have finished your changes, select commit, and the file is saved and propagated to all of its instances. When it's needed to either focus directly on the actors we are modifying or seeing the scene as a whole, we can toggle the level instance viewer in the visualization mode. Of course, there is so much going on here that we can use to better our own process, so I encourage you to take a look around and see the options available and how they are used in this sample project. Take advantage of these new tools and workflows that have been put together so that you and your team can work more efficiently on both small and large scale projects.
