Macros are the primary way to integrate C++ code with Unreal Engine, and expose functionality to the Editor. They provide metadata and functionality for Blueprints, networking, reflection, serialization, and other systems. UCLASS, USTRUCT, and UENUM are used to expose types to Unreal Engine, both for using in Blueprints and in the Editor. UPROPERTY exposes class members to Unreal Engine, both for Blueprints and in the Details panel. You can determine where the Property can be viewed, accessed, and edited. It enables automatic memory management of View Object pointers. It also enables networking and serialization functionality. It's very important that all class properties that reference UObjects be either a UPROPERTY reference or a WeakPtr type, so you don't get crashes if you try to access them after they get Garbage Collected. And lastly, UFunction exposes functions to Unreal Engine. These are the foundational building blocks of Unreal Engine. Unreal has its own standard library. You don't use the standard library from C++ at all. This allows better Editor integration, serialization support, and portability between platforms. For numbers, we have floats and doubles, the same as regular C++. For integers, however, we have explicitly-sized ints and (U)ints. The sizes of the plain int can vary between platforms. So it's important that for serialized and replicated properties you always use the explicitly sized integers. You can use plain ints if the variable isn't serialized at all-- for example, in for loops-- but it's a good habit to always prefer the explicitly sized ones. Enumerables can be created and exposed to the Engine. Structs are like classes, except they are only expected to keep plain data and can't have any Blueprint functions on them. Unreal has several string types, depending on your needs. FString is your standard plain string. It's a wrapper for a wide character array, and it is mutable. FName hashes and caches strings in a global map, which is then referenced from FNamed variables. Because they just store the index of the string, they allow super fast comparisons. They also have an index at the end, which you can increment without creating new strings. They're case insensitive, and are best used for names and paths. FText are strings with built in localization support. They get collected by the Engine's localization system for you to easily translate from a single source. These should be used for any user-facing text. Unreal has the standard collection types you would expect from any programming language, like arrays, maps, and sets. They are templated, can be exposed to Blueprints, and even support different memory allocators, like thread-safe, heap, or inline allocation. It also comes with ease of use transform types that support Blueprint and replication. There are lots of utility functions for these types in the FMath Library. UObject is the lowest level Unreal object which gets memory managed by the Engine. All classes extending it should be prefixed with a U. An Actor is anything that can be placed in a level. Extending classes should be prefixed with an A. Actors get automatically loaded and destroyed with their parent level. You can dynamically allocate new actors with the Spawn Actor function, and destroy them with the Destroy function. Besides making a new type of Actor, you can also add functionality to them with Components. Components contain the actual representation of what is placed in the level. The parent Actor is mostly a container. A Component can be either a UActor component, with no in-world representation, or UScene component, which has a transform relative to the parent Actor. Actors can have multiple Components of either type, and one routine Component from which all transforms are based from. Components are great for adding sets of functionality to different Actors without modifying their inheritance hierarchy. You should only allocate new UObjects with a NewObject function, and Actors with the SpawnActor function. UObjects get automatically destroyed when no other objects are referencing them. Actors can be removed from a level with the Destroy function, but the Garbage Collector will be what eventually releases the memory. Never try to manage the lifetime yourself through keywords like New, Delete, or Smart Pointers, which manage Lifetime. A very common mistake to make with UObjects is to have certain pointers to them without the UPROPERTY macro. They're not visible to the Garbage Collector, so the object can get collected and your left pointing to invalid data in memory, which can be very hard to debug. We have two sorts of Smart Pointers in Unreal Engine. UObject tracing works on the left, and non-UObject tracing works on the right. It is important that you never use the pointers on the right on any UObjects. Interfaces allow optional functions to be implemented by unrelated classes. This is unlike other programming languages, where classes must implement every function in an interface. In Unreal, an interface function can be called on any Object. And it will only be called if it's implemented. Interfaces can be declared in either C++ or as a Blueprint. It is, however, recommended to create interfaces in C++, so both C++ and Blueprint can use them, as Blueprint interfaces can only be used by other Blueprints. Static Function Libraries allow you to create Static Functions that can be called from anywhere. These are a good option for adding functionality to Structs. Data Objects give you a way of organizing and loading in data. They're a great way to structure your gameplay data. Data Assets are generic containers similar to data-only Blueprints. Data Tables have easy import and export functionality, and support Unreal Types. You can also create Curves as assets and reuse them in multiple places. Delegates and Events allow other Objects to subscribe to relevant events. These can be created from either C++ or Blueprint. However, if you want to subscribe to them in C++, then they need to be implemented in C++. Subsystems allow you to extend functionality easily and in a modular way, as they follow the lifetime authentic classes. They're like components to semantic classes, which you can access from anywhere. It keeps your code modular, easier to maintain, and easier to share between projects. Lastly, we have the Asynchronous Task Graph, which is an Engine-managed task graph which you can use to run work on multiple CPU cores or for asynchronous threaded work. It uses a thread pull internally, and multiple Engine systems already make use of it. In Unreal Engine, loading assets is mostly handled for you. Things either load in with a map or you can request an object be loaded from a soft reference. Objects then get unloaded by the Garbage Collector when nothing references them anymore. Anything that is referenced normally, as in through a heart reference, is automatically loaded recursively with the parent asset. This is convenient, but can backfire if you're not conscious of your references. A common pitfall is to reference too many things, where some assets can end up accidentally pulling in half of the project's other assets, which increase load times and memory both for the Editor and for shipping builds. Be mindful of your references, and use soft references and interfaces to reduce hard dependencies. The Garbage Collector automatically destroys objects that are either unreferenced or pending kill. It runs about once a minute, but you can override that. The Garbage Collector uses the mark and sweep method. The marking and sweeping is heavily multi-threaded and happens in a single frame, while the actual object destruction is time-sliced and happens over multiple frames. Unreal comes with a robust foundation, usable for most game types, which we call the Gameplay Framework. It supports multiplayer out of the box natively and robustly. We recommend you take advantage of the Gameplay Framework, instead of designing your systems around it, to really get the most out of Unreal. The GameMode is a per-level object that defines the rules for that level, like what Pawns to spawn, which HUD class, and so forth. One of the first things you do on a new project is to create your own GameMode class to override. For multiplayer games, this object instance only exists in the server. It defines the rules for the session, who can join, spectator rules, et cetera. It will not survive a hard-level transition, so it's not good for storing persistent data. For that, you can use the GameInstance. Every client has a GameInstance that persists throughout the entire application's lifetime. It's a global singleton that you can access from anywhere. You can either extend it for your project or, alternatively, you can create a GameInstance subsystem, which is kind of like a component for the GameInstance class. The GameState is an object that is replicated from the server to all clients. If GameMode is the object which states the max team points needed to win a match, then GameState is the object you'd use to keep track of the current points. It also keeps a list of all the PlayerStates. The PlayerState is game information that is specific to a given player. It's replicated from the server to all clients, and stores things like player name, score, and ping. But of course, you can extend this class and add your own data to it. A Pawn is an actor that a player can control. It's generic, and doesn't include much more than replication in it. A Character is a type of Pawn which has a movement component, a skeletal mass, and it can walk, run, fly, and swim. A Pawn is possessed by a Controller, which handles the inputs and commands to send to the Pawn to control it. The Controller can either be a human player or AI. You can switch possession of Pawns at any time during gameplay-- like for a player to switch from controlling the Character to controlling the vehicle the Character is in. The Controller is the brain of a Pawn. Each Player Controller is associated with a specific Player in their player's state. And the Player Controller only exists on the owning client and the server. The Player Controller allows the client to communicate with the server. To allow the most flexibility, you should always handle all input in the Controller class and not in the Pawn. That allows you to more easily switch out the Player Controller with an AI Controller without having to handle it in the Pawn itself. It handles its input through the Input Component. The Input Component binds input commands to game functionality. It is gradually being replaced by enhanced input. The Movement Component translates user input to in-game movements. It accounts for replication and it attempts to predict movement and account for lag. The Movement Component can be of different types-- projectile, interpolated, Pawn, Character, or vehicle. It can also be extended to provide custom movement. The Cheat Manager centralizes development Cheat and Debug commands in a single class. It gets compiled out in release build, so it's a safe way to add debugging functionality to your project safely without risk of shipping with unintended functionality. You can set which Cheat class to use in the Player Controller. We have a robust Ticking system in Unreal Engine. Each Actor and their components can register to tick. You can even add Ticking to UObjects. Ticks can run during different Tick groups, like before physics or during physics. It's smart to Tick Enduring Physics if you're not using Transforms or Collisions. You can define Tick rate, Tick dependencies, and enable or disable Ticking on a per-object basis. Ticks run single-threaded, so they can be a common point of congestion for games. Consider reducing Tick frequency for Objects that don't need to Tick every frame. The Gameplay Ability System is a multiplayer-ready framework for handling Gameplay Abilities in a modular and robust fashion. Mass allows you to define and manage a large number of game entities through distributed execution and State Graph. And lastly, Game Features plugins allow you to safely enable and disable functionality at runtime. These plugins depend on your project, not the other way around. So they allow your project to be feature agnostic, where the Game Features plugins register themselves into your game. By default, you can extend gameplay functionality by simply adding components to existing active classes. But you can also call functions or interfaces for deeper integration. Unreal Engine comes with built-in networking support out of the box. It's based on client and server type networking, where the server can either be another game instance or a dedicated server, which you can run as a HUD-less application. The Networking Framework does all the heavy lifting for you, like handling sessions, connections, and communication on each platform. Actors can easily be replicated to all clients with a simple checkbox. And you can mark each property you also want to be replicated. RepNotify allows you to execute some logic in response to the value of a replicated variable changing. For networking, we have the concept of ownership. So only Actors that are owned by the player controller are the ones that can send data to the server, while the server can send data to everyone. You have the option of using the Replication Graph plugin. The Replication Graph allows you to set rules for what makes an Actor relevant to other multiplayer clients, like based on distance, visibility, or other things. We use this on Fortnite to enable multiplayer matches between up to 100 players efficiently. Then we have Remote Procedure Calls, or RPCs, which allow you to call functions on different clients. You can mark an RPC to be run reliably, which will make sure it gets to its target destination. Or you can keep it as unreliable, in which case, the call could get dropped during heavy traffic. Unreal Engine comes with a suite of Profiling and Debugging tools, which complement well with native platform-specific tools. The best practice is generally to use both Unreal's and the platform's native tools for the most comprehensive Profiling and Debugging of your projects. Unreal uses a robust logging system, which uses both categories and verbosities. All logging goes through the UE_LOG macro for code, while you can use the Print String node in Blueprints. You have the option of both compile-time verbosities and runtime switching of verbosities. We also have the Visual Logger, a powerful Visual and time-based debug and logging tool. It records events into a timeline that can be played back afterwards in the Visual Logger panel. It allows you to record debug visuals and metadata for events. It also comes with support for logging network replication out of the box. The Visual Logger is easy to set up through macros and interfaces, and can be immensely useful for AI behavioral logging. built-in console which is compiled out in shipping builds, and allows you to either trigger console commands or to modify the value of console variables, also called CVARs. Most of the Engine's features can be configured through console variables. You can also make your own console functions or variables. A good practice is to expose functions of the TManager to be callable from the console. Unreal Insights is our new suite of profiling tools. With it, you can profile a lot of things, like CPU, TPU, memory allocations, and networking. It works both in the Editor and for package builds, except for shipping builds, unless you specifically enable it. It supports saving and replaying profiling data, as well as remote profiling over the network for profiling on other computers, or even devices. It uses instrumentation, and it's easy to add your own instrumentation macros for more granular profiling of your code. The CSV Profiler spits out data that you can then combine into a graph for frame timings. Low Level Memory, or LLM, gives each memory allocation a tag based on the stack that allocated it. Nowadays, though, Unreal Insights surpasses both these tools. ProfileGPU is a console command you can launch to inspect a single frame's timings. In the Editor, you'll get a UI for inspecting it, while otherwise the same data is printed in the output window. DumpGPU will dump out all internal resources of a single frame for inspecting as an interactive HTML page. You can launch it to inspect the draw calls, along with their internal buffers. And lastly, Gauntlet is a framework for running builds and validating them. Its purpose is to automate running sessions across multiple platforms. Because of that, it's great for automated testing. It can spawn a server and have multiple clients connect to it, for example.
